# 持续优化算子：本地代码与官方评测

在满足完整题目语义的前提下持续提高算子性能。自行管理上下文、优化方向、本地代码和实验记录，以真实官方结果评价改动。

没有正确实现时先建立正确性；已有正确实现时以它为基础探索性能优化。自主决定修改规模和优化组合，不要求每轮只验证一个猜想，也不要求每个优化技巧单独提交。

首次启动阅读本技能及同目录的 [TOOLS.md](TOOLS.md)。后续沿用当前会话，不把每次提交当成重新开始。使用宿主实际注册的工具 schema；本文不会创建工具，也不要求必须通过 MCP 提供。当前允许通过 app-server dynamic tools 使用。

## 可用能力

| 平台工具 | 用途 |
| --- | --- |
| `read_problem(url)` | 读取指定题目的完整 Markdown 题面 |
| `submit_official(...)` | 请求宿主冻结当前 workspace 的允许源码、保存快照并排队官方提交 |
| `read_official_evaluation(submission_id)` | 查询该提交的状态、编译诊断、正确性、性能、评分与测试点结果 |

模板由用户上传，宿主放入工作区。使用 Codex 自身文件工具读取、修改和管理版本，不调用模板读取工具。

当前没有自有 NPU 测试服务，不调用服务器测试工具，也不等待它部署。不直接操作平台数据库、官方凭据或绕过 Scheduler 提交。

## 1. 建立起点

1. 从启动消息取得题目 URL、workspace 路径、允许提交文件与只读文件说明，调用 `read_problem` 阅读题面。
2. 阅读上传文件，重点检查 `kernel.asc` 及必要的调用入口、类型定义和构建说明。有模板则基于模板；有用户指定的候选则先检查并沿用。不要先覆盖再阅读。
3. 没有模板时按题面和已有接口资料从零实现。缺少函数签名、参数布局或必要编译约定时指出缺失信息，不自创不兼容接口。
4. 明确 dtype、shape、广播、精度、边界、输出规则和评分目标。模板不等于已通过基线，注明验证状态。
5. 分开保存正确参考、性能最好版本和当前工作版本。不存在已验证 best 时记为空。

只修改允许的源码。`main.asc` 等宿主声明为只读的文件用于理解接口；备份、笔记和临时代码不进入官方载荷。

## 2. 自主选择与组合优化

根据题目语义、当前实现、历史结果和硬件特点，自主选择最有希望的优化方案。

允许算法调整、向量化、并行划分、数据布局、搬运、同步、融合、流水线和参数调节。可以一次实现多个相互配合的优化，不限制为标量路径、微小修改或逐项验证。

修改前简要记录准备解决的瓶颈、主要改动和预期效果即可。无需为每个技巧分别建立实验，也不要求先完成长篇分析才能写代码。记录公开分析摘要，不要求输出内部思维链。

优化组合应有依据，考虑改动之间的依赖与资源竞争。不要为了增加技巧数量而堆叠不适用的改动。

自主选择继续修改当前候选、从 best 开新分支、复用历史实现或重构主要计算路径。保留已验证的最好版本，避免探索性修改覆盖唯一可恢复的正确实现。

组合方案获得收益时，可以直接保留并继续优化；不强制拆开每项改动测量贡献。只有在定位错误、解释退化或指导下一步确有价值时，才进行单因素实验或消融。

## 3. 连续实现、修复与探索

在本地实现候选 v1，读取反馈后继续修改为 v2、v3。版本编号只用于追溯，不代表必须采用固定轮次或固定修改粒度。

编译错误或 WA 后，先读取产生反馈的实际代码，再决定修复方式。不要自动回到模板重写而丢掉已有修正。

能够根据诊断定位问题时，直接修复当前候选。组合改动使问题难以定位时，可以拆分修改、暂时关闭某项优化、回退部分代码，或从已验证版本重新组合。选择最有助于推进的方式，不要求始终沿同一个失败版本继续修补。

正确但没有提速时，检查：

- 优化是否真正进入执行路径。
- 分块、并行度、缓冲和其他参数是否适配目标输入。
- 新增开销是否抵消收益。
- 多项优化之间是否存在资源竞争或性能冲突。
- 收益是否只出现在部分输入，是否被其他测试点退化抵消。

据此自主选择调参、替换实现、撤销部分改动、复测或更换方向。一个配置无收益不等于整个方向无效，但也不要求穷举所有参数才能继续探索。

对不熟悉的 API，利用实际可用的本地资料、头文件、示例或检索能力核对版本和参数。无法查证时明确不确定性，不假装已经核对。反复编译失败时整理错误与接口证据，不继续无依据地猜函数名。

## 4. 提交前检查

检查完整源码和实际 diff：

- 新计算是否进入输出路径，旧实现是否真正被替换。
- 参数调整是否影响目标输入。
- 要求的 dtype、shape 和边界是否覆盖。
- 索引、同步、精度和资源使用是否合理。
- 多项改动组合后是否仍满足题目合同。

注释变化、未调用函数或代码中出现某个 API 名称，不能证明优化已经实现。

若本地确实存在匹配的编译测试环境，可辅助检查；没有环境时记录“尚未编译”，通过官方评测验证。静态检查不能当作编译或正确性通过。

保存文件后调用 `submit_official`，参数以实际 schema 为准。宿主读取 workspace 并冻结源码，不要求在参数中重复粘贴整份代码。

保存返回的 `submission_id`、快照和源码摘要。提交采集期间不修改提交文件，收到冻结成功响应后才继续编辑。

新候选使用普通提交；有目的的同源码复测使用宿主支持的复测参数。若工具没有复测能力且拒绝相同代码，报告复测受阻，不靠修改注释绕过。

网络重试不等于独立复测。按工具幂等约定处理，提交状态不明时不盲目重发。

## 5. 根据真实反馈决策

用返回的本平台 `submission_id` 调用 `read_official_evaluation`，不替换为 `remote_id`。按建议间隔轮询；未给出间隔时合理退避，避免高频空查。

排队或运行中不是评测结论。等待期间可以阅读资料、分析源码或准备后续候选，但不能假设未返回的结果，也不能混淆不同版本的反馈。

评测只对应冻结的快照，不对应后来变化的工作区。

| 反馈 | 下一步 |
| --- | --- |
| 编译错误 | 阅读具体诊断，检查类型、API、模板和 host/device 使用；修复当前候选，必要时拆分或回退部分改动 |
| WA / 部分通过 | 检查失败输入、语义、dtype、边界、索引、同步与精度；必要时隔离组合改动，不覆盖性能 best |
| 完整通过且性能改善 | 保存候选及证据，按既定指标更新 best，并自主继续探索 |
| 正确但无明显收益或退化 | 检查实现是否落实、参数与优化之间是否冲突，再决定调参、复测、部分回退或换方向 |
| 日志或覆盖不足 | 明确未知，必要时请求补充诊断，不伪造原因和覆盖范围 |
| 认证、配额、网络故障 | 保存现场并报告外部阻塞，不当作候选代码失败 |

优先按官方评分目标比较；没有明确目标时沿用用户指定指标，不擅自对所有题目使用 `max_time`。不要用正确率代替性能。

记录耗时单位、逐点表现和测试覆盖。不同环境或测试集的结果不能直接混排。

区分官方宣告 Pass、已知完整覆盖和仅返回的部分测试通过。只有满足正确性要求且性能结果可比的候选，才能成为已验证的性能 best。

小幅收益或波动明显的结果按需进行独立复测。未经复测可以记录“本次观测到提升”，不能声称收益稳定可重复。复测尚未完成不妨碍保存候选和继续其他有价值的探索。

组合修改带来收益时，记录“这组改动有效”。未经拆解验证，不声称每个技巧都单独有效；没有相应证据，不因一次提速就宣称硬件流水重叠等机制已被证明。

## 6. 保存进展并持续推进

在本地保留可恢复源码和简短笔记，至少记录：

- 当前 best、当前工作版本及其验证状态。
- 每个重要候选的来源版本、主要改动或优化组合。
- 提交 ID、快照摘要和对应结果。
- 已验证事实、暂时推测、失败或退化情况。
- 未决评测和下一步。

记录服务于后续决策，不要求为每次修改填写冗长报告。会话压缩或恢复后先读取必要记录和相关代码，再继续。

区分实现未完成、已测配置无收益、组合方案有效、证据不足和外部阻塞。不要把有限配置的失败写成永久无效方向，也不要无新依据地重复同一失败方案。

自主决定何时继续当前方案、何时重构、何时从 best 探索其他方案。无需把每个技巧逐项验证完，才能进行下一次组合优化。

不设固定修订次数、累计提交预算或连续无提升停止次数，由用户暂停或停止。遵守平台限频、在途限制、单次执行限制和外部真实配额。

取得一次 Pass 或一次提升后可以继续，不必每次提交都请求确认。持续优化不等于机械重复；当进展停滞时，重新审视瓶颈、实现路线和已有证据，调整策略。

暂停或停止后不再新提交，保留未决 ID；不声称撤销了已被官方接收的任务。持续外部故障或缺少必要接口导致无法继续时保存状态并说明阻塞，不空转。

进度报告只包含真实修改、评测证据和未解决问题。
