# 持续优化算子：本地代码与官方评测

在满足完整题目语义的前提下持续提高算子性能。自行管理上下文、优化方向、本地代码和实验记录，以真实官方结果验证猜想。没有正确实现时先建立正确性，已有正确实现时以它为基础优化。

首次启动阅读本技能及同目录 [TOOLS.md](TOOLS.md)。后续沿用当前会话，不把每次提交当成重新开始。使用宿主实际注册的工具 schema；本文不会创建工具，也不要求必须通过 MCP 提供。当前允许通过 app-server dynamic tools 使用。

## 可用能力

| 平台工具 | 用途 |
| --- | --- |
| `read_problem(url)` | 读取指定题目的完整 Markdown 题面 |
| `submit_official(...)` | 请求宿主冻结当前 workspace 的允许源码、保存快照并排队官方提交 |
| `read_official_evaluation(submission_id)` | 查询该提交的状态、编译诊断、正确性、性能、评分与测试点结果 |

模板由用户上传，宿主放入工作区。使用 Codex 自身文件工具读取、修改和管理版本，不调用模板读取工具。当前没有自有 NPU 测试服务，不调用服务器测试工具，也不等待它部署。不直接操作平台数据库、官方凭据或绕过 Scheduler 提交。

## 1. 建立起点

1. 从启动消息取得题目 URL、workspace 路径、允许提交文件与只读文件说明，调用 read_problem 阅读题面。
2. 阅读上传文件，重点检查 kernel.asc 及必要的调用入口、类型定义和构建说明。有模板则基于模板；有用户指定的候选则先检查并沿用。不要先覆盖再阅读。
3. 没有模板时按题面和已有接口资料从零实现。缺少函数签名、参数布局或必要编译约定时指出缺失信息，不自创不兼容接口。
4. 明确 dtype、shape、广播、精度、边界、输出规则和评分目标。模板不等于已通过基线，注明验证状态。
5. 分开保存正确参考、性能最好版本和当前工作版本。不存在已验证 best 时记为空。

只修改允许的源码。main.asc 等宿主声明为只读的文件用于理解接口；备份、笔记和临时代码不进入官方载荷。

## 2. 围绕一个猜想连续推进

每轮从已验证的性能最好版本开始；没有它时从现有实现或空实现开始建立正确性。基于代码和反馈提出可检验猜想，简述证据、作用机制、实际改动、预期受益输入和验证方法。记录公开分析摘要即可，不要求输出内部思维链。

在本地实现 v1，读取反馈后继续修为 v2、v3。编译错误或 WA 后，先读取产生反馈的实际版本，再修复它；不要自动回到 best 或模板重写而丢掉已有修正。主动回退或换方向时记录理由。

保留本轮代码、修改、假设与结果的对应关系。实现尚未正确不证明性能方向无效。正确但未提速时，检查改动是否真正生效、参数是否适配输入，再进行有依据的参数探索和复测。一个配置无收益不等于整个方向无效，但也不要求无限穷举。

允许算法调整、向量化、并行、布局、搬运、同步、融合和参数调节，不限制为标量路径或每次只改一行。独立因素尽可能分开验证；组合改动有效时不直接归因于其中某个因素。

对不熟悉的 API，利用实际可用的本地资料、头文件、示例或检索能力核对版本和参数。无法查证时明确不确定性，不假装已经核对。反复编译失败时整理错误与接口证据，不继续无依据地猜函数名。

## 3. 提交前检查

检查完整源码和实际 diff：新计算是否进入输出路径、旧实现是否真正替换、参数是否影响目标输入、要求的 dtype 是否覆盖、边界和资源使用是否合理。注释变化或未调用函数不能证明优化实现。

若本地确实存在匹配的编译测试环境，可辅助检查；没有环境时记录“尚未编译”，通过官方评测验证。静态检查不能当作编译或正确性通过。

保存文件后调用 submit_official，参数以实际 schema 为准。宿主读取 workspace 并冻结源码，不要求在参数中重复粘贴整份代码。保存 submission_id、快照和源码摘要。提交采集期间不修改提交文件，收到冻结成功响应后才继续编辑。

新候选使用普通提交；有目的的同源码复测使用宿主支持的复测参数。若工具没有复测能力且拒绝相同代码，报告复测受阻，不靠修改注释绕过。网络重试不等于独立复测，按工具幂等约定处理，提交状态不明时不盲目重发。

## 4. 根据真实反馈决策

用返回的本平台 submission_id 调用 read_official_evaluation，不替换为 remote_id。按建议间隔轮询；未给出间隔时合理退避，避免高频空查。排队或运行中不是结论，到达终态后读取诊断再决定修改。

评测只对应冻结的快照，不对应后来变化的工作区。

| 反馈 | 下一步 |
| --- | --- |
| 编译错误 | 阅读具体诊断，检查类型、API、模板和 host/device 使用，基于失败版本修复 |
| WA / 部分通过 | 检查失败输入、语义、dtype、边界、索引、同步与精度，不覆盖性能 best |
| 完整通过 | 按官方目标比较性能、逐点退化及测量可比性 |
| 正确但无明显收益 | 检查实现是否落实，调参并复测，证据足够后再结束方向 |
| 日志或覆盖不足 | 明确未知，必要时请求补充诊断，不伪造原因和覆盖范围 |
| 认证、配额、网络故障 | 保存现场并报告外部阻塞，不当作候选代码失败 |

优先按官方评分目标比较；没有明确目标时沿用用户指定指标，不擅自对所有题目使用 max_time。不要用正确率代替性能。记录耗时单位与测试覆盖；不同环境或测试集的结果不能直接混排。

区分官方宣告 Pass、已知完整覆盖和仅返回的部分测试通过。小幅收益通过独立复测判断；没有新测量就不能声称可重复。一次提速不证明硬件流水重叠，除非另有证据。

## 5. 保存进展并继续

在本地保留可恢复源码和简短笔记：best 与 working、每轮猜想、父版本、实际修改、提交 ID 与快照摘要、编译/正确性/性能结论、未决评测及下一步。会话压缩或恢复后先读记录和相关代码，再继续。

区分实现未完成、已测配置无收益、观测到提升、证据不足和外部阻塞。有限配置的失败不是永久无效方向。结束一个方向后从当前最好版本选择新方向，不丢失已有有效改动。

不设固定修订次数、累计提交预算或连续无提升停止次数，由用户暂停或停止。遵守平台限频、在途限制、单次执行限制和外部真实配额。取得一次 Pass 或一次提升后可以继续，不必每次提交都请求确认。

暂停或停止后不再新提交，保留未决 ID；不声称撤销了已被官方接收的任务。持续外部故障或缺少必要接口导致无法继续时保存状态并说明阻塞，不空转。进度报告只包含真实修改、证据和未解决问题。
